Files in a `nebula create` project: `src/object-properties.js` (initial properties), `src/data.js` (data targets), `src/ext.js` (panel and `support`), `src/index.js` (wiring). Same split as https://qlik.dev/extend/extensions/nebula-js/quickstart/migrate-vis-extension-nebula/.

## initialProperties -> `qae.properties`

```js
// legacy
initialProperties: {
  qHyperCubeDef: { qDimensions: [], qMeasures: [], qInitialDataFetch: [{ qWidth: 2, qHeight: 500 }] },
  barColor: '#3b82f6',
}
```

```js
// src/object-properties.js
const properties = {
  showTitles: true, title: '', subtitle: '', footnote: '',   // generated by the scaffold; keep
  qHyperCubeDef: { qInitialDataFetch: [{ qWidth: 2, qHeight: 500 }] },
  barColor: '#3b82f6',
};
export default properties;
```

Rules:

1. Keep every custom property name and nesting exactly as before. Saved objects store values at those paths.
2. Empty `qDimensions` / `qMeasures` arrays can be dropped; the data target creates them.
3. **Move each `defaultValue` from the old `definition` into the initial properties** as well (the qlik-oss migrations did this). Initial properties apply only to objects created after the new extension is installed; the property panel `defaultValue` does not fill the layout of an existing object.
4. Keep `qInitialDataFetch` at most 10,000 cells per page (`qWidth * qHeight`). Page with `getHyperCubeData` for more; see `selections-and-data.md`.
5. A list-object extension uses `qListObjectDef` and a `/qListObjectDef` target.
6. Optional: record a `version` property (qlik-oss charts set it from `process.env.PACKAGE_VERSION` through `build.replacementStrings` in `nebula.config.js`), so later property migrations can tell old from new.
7. Dynamic properties are those starting with `q` plus a capital letter; the engine evaluates them. Rendering code reads the **layout**, never the properties.

## definition -> `ext.definition`

Copy the whole panel object into `ext.definition` and change only the data sections:

```js
// legacy
dimensions: { uses: 'dimensions', min: 1, max: 1 },
measures:   { uses: 'measures',   min: 1, max: 1 },
```

```js
// src/ext.js
data: { uses: 'data' },
```

`sorting`, `addons` and `settings` (`uses:`) stay, but open the panel in your host and check that each section shows what the legacy panel showed. Your own sections, `ref` paths, `label`, `type`, `component`, `defaultValue`, `show`, `expression` and `options` carry over. `uses: 'data'` is in the official migration tutorial and Qlik's own charts.

**The Data section is mandatory when `qae.data.targets` is declared.** Without `data: { uses: 'data' }` Sense shows the *sheet's* property panel when the object is selected, with no console error, and the extension still renders. `scripts/check-panel.mjs` fails on this (verified in Qlik Cloud, October 2026). Only omit the section by declaring `targets: []`, and then `check-compat.mjs` reports the data path as removed.

Check while copying:

- Labels built with the AngularJS translator or `qlik` objects: use `galaxy.translator.get(...)` (`ext(galaxy)` runs outside `component()`, so no hooks).
- `show` callbacks are evaluated by the Sense client and receive the object's properties (your `ref` paths: `data.linkColumns`, or `data.props.x` where the legacy code nested them). An object created by API or an old save can lack a nested object, so read defensively (`data.props?.x`).
- `{ template, controller }` components are AngularJS: replace them (`host-isolation.md`).
- `nebula serve` does not render `ext.definition`; only Sense exercises it.

## Per-row colors, labels and tooltips (attribute expressions)

Legacy extensions that let the user type an expression per dimension or measure (color by expression, label, tooltip) keep it in `qAttributeExpressions` and read each cell's `qAttrExps.qValues[i]`. In nebula the panel item goes inside the data section. Verified in Qlik Cloud in October 2026: this adds an expression field under the dimension in the panel.

```js
data: {
  uses: 'data',
  items: {
    dimensions: {
      items: {
        attributes: {
          component: 'attribute-expression-reference',
          ref: 'qAttributeExpressions',
          defaultValue: [],
          items: [{ component: 'expression', ref: 'qExpression', label: 'Color expression', id: 'colorExpression', tid: 'colorExpression' }],
        },
      },
    },
  },
}
```

That test covered the panel only. Whether the engine returns `qAttrExps` for your cells, and for measures as well as dimensions, is yours to test. Keep the same `ref` and ids the legacy panel used, or saved expressions are lost (`check-compat` compares refs).

## Calculation condition and data handling

A legacy extension that exposed a calculation condition nested it under the add-ons. Put `dataHandling: { uses: 'dataHandling', items: { calcCond: { uses: 'calcCond' } } }` in the items of your `addons` section. Verified in Qlik Cloud in October 2026: next to the extension's own add-on items, the panel showed "Data handling" with "Include zero values" and a "Calculation condition" expression field.

## Per-field items, master items and alternatives

- `uses: 'data'` replaces the legacy `dimensions`/`measures` sections. To add an item to every dimension or measure, put it under `items.dimensions.items.<name>` or `items.measures.items.<name>` (the example above).
- A dimension or measure taken from the master library is referenced by `qLibraryId`; its title comes from the library item (`Doc.getMeasure(id)` or `getDimension(id)`, then `getLayout()`), not from `qDef`. Check the label in your host.
- The Data section of a nebula extension in Qlik Cloud offers "Alternative dimensions" and "Alternative measures" (observed October 2026). Whether switching to an alternative renders correctly in your extension is untested here: test it, and keep the legacy extension's `qLayoutExclude` handling if it had any.

## Extensions without data

An extension that has no dimensions, measures or list (it reads the app through the engine, or is a launcher) declares `targets: []`, has no Data section, and needs no `qHyperCubeDef`. `check-panel` and `check-compat` handle that (`nothing-to-compare` for the data path is expected). Set `support` from the legacy flags; with none, use the documented defaults (`snapshots-and-export.md`), not the scaffold's `viewData: true`.

## `support`

```js
support: { snapshot: true, export: true, exportData: true, viewData: false }
```

Copy the old flags. A flag may also be a function of the layout. Meaning and Qlik Cloud limits are in `snapshots-and-export.md`.

## Data targets (`src/data.js`)

```js
export default {
  targets: [
    { path: '/qHyperCubeDef', dimensions: { min: 1, max: 1 }, measures: { min: 1, max: 1 } },
  ],
};
```

- Take `min` / `max` from the old `dimensions` / `measures` sections. `min` and `max` may be functions of the properties. If `min` is not reached, stardust shows a placeholder and does not call `component()`.
- Optional hooks per field target: `added(dim)`, `removed(dim)`, `description(props)`. Use `added` for per-field defaults such as `dim.qNullSuppression = true`.
- Keep the same `path` as the old `initialProperties` (`/qHyperCubeDef` or `/qListObjectDef`); `scripts/check-compat.mjs` fails if it changes.
- If you changed a limit, `check-compat.mjs` reports it: tightening a limit makes saved objects within the old limit render as a placeholder.

## Migration of old property shapes

If the new extension must read an older property layout, handle it in the rendering code with a fallback (`layout.x ?? default`). Qlik's own charts also use `ext.migrate` (for example `migrate: { properties(props) {...} }` in sn-org-chart) which the Sense client honors; treat it as host-specific and verify it, because it is not part of the stardust API.
